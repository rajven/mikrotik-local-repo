## 📖 О проекте

Автономное трёхуровневое решение для парка устройств MikroTik без доступа в Интернет (или с ограниченным доступом):

1. **Зеркало** — Bash-скрипты синхронизации загружают пакеты RouterOS 6 и RouterOS 7, Winbox и файлы Netinstall из официальных репозиториев (`upgrade.mikrotik.com` / `download.mikrotik.com`) в корень веб-сервера.
2. **Прокси обновлений** — PHP-обработчики перехватывают запросы RouterOS о доступных версиях (`NEWEST6.*`, `NEWESTa7.stable` и т. п.), кэшируют ответы и отдают сами файлы пакетов с того же хоста.
3. **Политика обновлений** — каждое планируемое обновление проверяется по серийному номеру устройства, модели или глобальному правилу. Правила настраиваются через веб-интерфейс. Если ни одно правило не совпало, решение принимает встроенный «безопасный» список из `mt_proxy_config.php`, — роутер никогда не обновится до непроверенной версии.

Устройства направляются на зеркало статическими DNS-записями, поэтому RouterOS «думает», что общается с MikroTik:

```
/ip dns static add address=192.168.0.1 name=download.mikrotik.com
/ip dns static add address=192.168.0.1 name=upgrade.mikrotik.com
```

## ✨ Возможности

**Зеркало**

- 🔄 RouterOS 6 (stable + LTS/`6fix`) и RouterOS 7 (stable + long-term).
- 🏗 Все поддерживаемые архитектуры: `arm`, `arm64`, `mipsbe`, `mmips`, `ppc`, `smips`, `tile`, `x86`.
- 📦 Архивы `all_packages-*.zip` **скачиваются и распаковываются** — отдельные `.npk` доступны для ручных обновлений.
- 📥 Winbox всех опубликованных версий (`.zip`, `.dmg`, `.sha256`) в отдельном дереве `winbox/`.
- 📄 Дополнительные файлы: `CHANGELOG`, `packages.csv`, Netinstall, ISO-образы, установщик The Dude, `.mib`, `btest.exe`, `flashfig.exe`.
- ⏩ Неизменившиеся версии пропускаются — скачиваются только новые или обновлённые релизы. Каждый файл проверяется по `Content-Length` сервера (архивы дополнительно по CRC), поэтому `force` перепроверяет релиз и перезагружает только повреждённое или отсутствующее. Каждую заново — лишь `CHANGELOG` и `packages.csv`.
- 🎯 `download_ros.sh` загружает одну конкретную версию, включая старые релизы.

**Прокси обновлений**

- 🛰 Проксирует и кэширует ответы `NEWEST6/NEWESTa6/NEWEST7/NEWESTa7` для каналов `.stable`, `.long-term` и `.upgrade`.
- 🔥 `ros-warmup.php` после каждой синхронизации прогревает кэш версий, используя версии прошивок реально зарегистрированных в базе устройств, — первый запрос устройства не уходит в Интернет. Эндпоинт защищён секретным токеном.
- 🔀 Работает с Apache (FPM **или** mod_php, автоопределение) и Nginx; готовые конфигурации — в `addons/`.

**Политика обновлений**

- 🚦 `force_update.php` возвращает `ENABLED` / `DISABLED` для запрошенной версии.
- 🗂 Правила задаются по серийному номеру, по модели (`model:RB4011`) или глобально, с фиксированным приоритетом.
- 👀 Устройства регистрируются автоматически при первом запросе: серийный номер, модель, имя устройства, IP-адрес, текущая и целевая версии прошивки, время последнего появления.
- 🖥 Веб-админка (Basic Auth + SQLite): поиск, пакетное редактирование, глобальный allow-лист версий и просмотр `CHANGELOG` загруженных версий.
- 🤖 Скрипты для самих роутеров: резервное копирование по расписанию (`.backup` + `/export`), обновление RouterOS и прошивки RouterBOARD, защита от цикла перезагрузок, самообновляемый установщик.

## 🧭 Как это работает

```
     Интернет: upgrade.mikrotik.com / download.mikrotik.com
                │
                │  только во время синхронизации: wget + curl + unzip
                ▼
 ┌──────────────────────────────────────────────────────────────┐
 │  Сервер-зеркало  (/var/www/html)                             │
 │                                                              │
 │  routeros/                 пакеты, .npk, Winbox, changelog   │
 │  routeros/*.version.cache  кэш ответов прокси-уровня         │
 │  mt-proxy/                 PHP-обработчики + SQLite + UI     │
 └──────────────────────────────▲───────────────────────────────┘
                                 │  запросы версий, скачивание пакетов,
                                 │  проверка политики (ENABLED / DISABLED)
                       Роутер MikroTik (без доступа в Интернет)
                       Статический DNS: download|upgrade.mikrotik.com → зеркало
                       Цикл обновления запускает BackupAndUpdate.rsc
```

Цикл обновления устройства:

1. Устройство запрашивает `upgrade.mikrotik.com/routeros/NEWEST7.stable` — PHP-прокси отвечает из кэша, с вышестоящего сервера или из запасного значения.
2. Запросы `NEWESTa*` / `NEWEST6.*` с параметром `?version=X` обрабатываются так же. Так RouterOS узнаёт о релизах ROS 7 начиная с 7.12.1 и о переходе с ROS 6 на ROS 7.
3. Устройство скачивает файлы `.npk` / `all_packages` с `/routeros/<version>/` на том же хосте.
4. Скрипт `BackupAndUpdate`, запускаемый по расписанию, отправляет серийный номер, модель и целевую версию в `/routeros/force_update.php`.
5. Если сервер отвечает `ENABLED`, скрипт создаёт резервную копию и устанавливает обновление. При `DISABLED` установка отменяется, но состояние устройства всё равно фиксируется в инвентарной базе.

## 📋 Требования

Debian / Ubuntu и следующие пакеты:

| Компонент                                             | Для чего                             |
| ----------------------------------------------------- | ------------------------------------ |
| `bash`, `wget`, `curl`, `unzip`, `coreutils`          | Скрипты синхронизации                |
| `php-curl`, `php-sqlite3`                             | Прокси, политика, веб-админка        |

## 🚀 Установка

Все примеры рассчитаны на стандартную раскладку Debian: скрипты в `/usr/local/bin`, корень веб-сервера `/var/www/html`, зеркало — `/var/www/html/routeros`.

### 1. Установка пакетов

**Apache**

```
apt install git bash wget curl unzip php php-curl php-sqlite3 php-fpm apache2 -y
a2enmod rewrite headers proxy_fcgi setenvif
a2enconf php8.3-fpm        # укажите свою версию PHP
```

**Nginx**

```
apt install git bash wget curl unzip php php-curl php-sqlite3 php-fpm nginx -y
```

> В пуле PHP-FPM установите `clear_env = no`, если планируете переопределять параметры переменными окружения.

### 2. Установка скриптов синхронизации

```
git clone https://github.com/rajven/mikrotik-local-repo.git
cd mikrotik-local-repo

cp scripts/*.sh /usr/local/bin/
chmod +x /usr/local/bin/sync_mikrotik_repo.sh \
         /usr/local/bin/download_ros.sh
```

### 3. Установка веб-слоя

```
mkdir -p /var/www/html/routeros
cp -r html/mt-proxy             /var/www/html/
cp    html/routeros/*.cache     /var/www/html/routeros/
cp    html/fullchain.pem        /var/www/html/
cp    addons/mikrotik/*.rsc     /var/www/html/routeros/   # скрипты для устройств
chown www-data:www-data -R /var/www/html
```

Скрипты для роутеров поставляются в двух форматах: `*.txt` — читаемый исходник, `*.rsc` — тот же скрипт, обёрнутый в `/system script add`, готовый к импорту. Устройствам достаточно отдавать `.rsc`. Обе поставляемые конфигурации веб-сервера намеренно отдают `*.rsc` и `*.txt` из `/routeros/` **только клиентам RouterOS** (User-Agent `Mikrotik/6.x…Fetch`, `Mikrotik/7.x…Fetch` или `RouterOS 7.x…`); попытка скачать их через `curl` или браузер вернёт 403.

`fullchain.pem` — цепочка сертификатов, которую `BackupAndUpdate` импортирует в хранилище сертификатов RouterOS 6 перед HTTPS-проверкой политики. Положите туда CA-цепочку своего сервера или используйте пример только для тестов. Файл нужен только если устройства ROS 6 обращаются к серверу политики по HTTPS. Для ROS 7 — не требуется, как и при работе политики по HTTP.

### 4. Настройка веб-сервера

**Apache**

```
cp addons/apache/conf-available/php-autodetect.conf /etc/apache2/conf-available/
cp addons/apache/sites-available/00-mirror.conf     /etc/apache2/sites-available/
a2enconf php-autodetect
a2ensite 00-mirror
a2dissite 000-default

htpasswd -c /etc/apache2/.htpasswd admin     # пароль веб-админки
systemctl reload apache2
```

`php-autodetect.conf` выбирает `PHP_MODE_FPM`, если найден сокет PHP-FPM и включён `mod_proxy_fcgi`; иначе выбирается `PHP_MODE_MODPHP`. Vhost содержит маршрутизацию для обоих режимов.

**Nginx**

```
cp addons/nginx/conf.d/mikrotik_ua.conf /etc/nginx/conf.d
cp addons/nginx/snippets/mt-fastcgi.conf /etc/nginx/snippets/
cp addons/nginx/site.conf               /etc/nginx/sites-available/mirror
ln -sf /etc/nginx/sites-available/mirror /etc/nginx/sites-enabled/mirror

htpasswd -c /etc/nginx/.htpasswd admin   # пароль веб-админки
nginx -t && systemctl reload nginx
```

> 📝 В обеих конфигурациях жёстко прописаны `server_name download.mikrotik.com upgrade.mikrotik.com` (в Apache — закомментировано) и пути внутри `/var/www/html`. Подгоните `ServerName` / `server_name`, путь к сокету FPM и корень документа под своё окружение.

Каталог `/routeros` **обязан** находиться в корне сайта: устройства запрашивают пути вида `/routeros/7.24.5/routeros-arm64-7.24.5.npk`, а прокси-эндпоинты сопоставляются как `/routeros/NEWEST…`. Раздача зеркала из подкаталога ломает и то, и другое.

### 5. Синхронизация по расписанию

```
cp addons/cron.d/sync_ROS_repo /etc/cron.d/
chmod 644 /etc/cron.d/sync_ROS_repo
```

```
1 */3 * * * root /usr/local/bin/sync_mikrotik_repo.sh 2>/dev/null && chown www-data:www-data -R /var/www/html
```

Запускается каждые три часа от root и передаёт свежие файлы пользователю веб-сервера.

### 6. Первый запуск

```
mkdir -p /var/www/html/routeros
/usr/local/bin/sync_mikrotik_repo.sh force
chown www-data:www-data -R /var/www/html
```

Проверьте, что прокси отвечает локально:

```
curl -i "http://localhost/routeros/NEWEST7.stable"          # сначала X-Cache: MISS, затем HIT
curl  "http://localhost/routeros/force_update.php?new_version=7.24.5&serial=TEST&model=RB5009"
```

Второй запрос регистрирует в базе устройство с серийным номером `TEST`. На свежей установке глобальный список версий пуст, поэтому решение принимает уровень 5 (встроенный allow-лист): `7.24.5` вернёт `ENABLED`, а версия вне списка — `DISABLED`. Чтобы забрать управление у встроенных значений, добавьте свои версии в разделе **Global versions** веб-админки.

### Альтернатива: Docker

В каталоге `docker/` лежит готовый all-in-one образ (nginx + PHP-FPM, цикл
синхронизации внутри — настройка веб-сервера и cron не нужны):

```
git clone https://github.com/rajven/mikrotik-local-repo.git
cd mikrotik-local-repo/docker
cp .env.example .env      # заполнить SITE_URL, WARMUP_TOKEN, ADMIN_PASSWORD
docker compose up -d --build
docker compose logs -f    # первая синхронизация — через ~90 с
```

Всё состояние (зеркало, SQLite, конфиги) живёт в хост-каталоге
`MIRROR_DATA_DIR` (из `.env`, по умолчанию `./data`), монтируемом в `/data`.
При каждом старте контейнер подставляет `SITE_URL` в device-копии `.rsc`,
резолвит `SERVER_IP` для `dns.rsc`, пересобирает все `.md5` и передаёт `TZ`
в PHP-FPM. Настройка устройств (статический DNS, скрипты) — точно такая же,
как в шагах выше. Подробности: [`docker/README.md`](docker/README.md).

## ⚙️ Конфигурация

### Скрипты синхронизации — `scripts/config.sh`

```
TARGET_DIR="/var/www/html/routeros"   # корень зеркала, раздаётся веб-сервером
SITE_URL="http://localhost"           # базовый URL для обращения к ros-warmup.php
WARMUP_TOKEN="CHANGE_ME"              # секретный токен эндпоинта прогрева кэша
WGET="/bin/wget"                      # путь к wget; иначе ищется в $PATH
LOG_OFF=0                             # 1 — полностью отключить логирование в syslog
URL_SCHEMA="https"                    # http|https для upgrade.mikrotik.com; некорректное значение → http
WGET_OPTS="-q --timeout=15 --read-timeout=60 --tries=2"  # без -nc: размеры сравнивает сам fetch_file()
SYNC_LOCK_FILE="/tmp/mikrotik-local-repo.sync.lock"      # общий замок sync и download_ros.sh
ROS6_CACHE_FILE="${TARGET_DIR}/ros6.version.cache"       # очищается при повышении релиза
ROS7_CACHE_FILE="${TARGET_DIR}/ros7.version.cache"

versions6=("6" "6fix")                # каналы ROS 6: stable и LTS
versions7=("stable" "long-term")      # каналы ROS 7
firmware_arch=("arm" "arm64" "mipsbe" "mmips" "ppc" "smips" "tile" "x86")

additional_files=( ...)               # Netinstall, ISO, служебные файлы, .mib и т. д.
WINBOX_DIR="${TARGET_DIR}/winbox"     # Winbox всегда загружается по HTTPS
```

Удалите неиспользуемые архитектуры из `firmware_arch` — это самый большой выигрыш по времени синхронизации и месту на диске.

### Прокси и политика — `html/mt-proxy/mt_proxy_config.php`

Файл возвращает массив конфигурации:

| Ключ                               | Назначение                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------|
| `upstream_base`                    | Префикс официального репозитория (`https://upgrade.mikrotik.com/routeros/`)               |
| `connect_timeout`, `total_timeout` | Таймауты обращений к upstream, сек (2 / 3)                                                |
| `cache_revalidate`                 | Возраст записи кэша, после которого ответ `NEWEST*` снова запрашивается у upstream (21600 с) |
| `routeros_dir`                     | Каталог зеркала, вычисляется из `DOCUMENT_ROOT`                                           |
| `WARMUP_TOKEN`                     | Секретный токен `ros-warmup.php`; должен совпадать с `WARMUP_TOKEN` в `scripts/config.sh` |
| `allowed_versions_hardcoded`       | Allow-лист последней инстанции (`6.49.23`, `7.24.5`, `7.23.8`)                            |
| `fallbacks`                        | Запасные ответы по каждому эндпоинту, когда недоступны и upstream, и локальные маркеры    |
| `v6` / `v7`                        | Префикс журнала, файл кэша, версия по умолчанию, префикс `User-Agent`, локальные маркеры  |

Редактируйте `mt_proxy_config.php`, когда MikroTik выпускает новые версии и вы хотите обновить запасные значения. Файл правил `mt_proxy_rules.php` больше не поставляется: правила хранятся в SQLite. Старый `mt_proxy_rules.php`, оставшийся в `mt-proxy/`, по-прежнему учитывается как уровень приоритета 4 и однократно импортируется в базу при первом подключении.

## 🔄 Синхронизация

```
/usr/local/bin/sync_mikrotik_repo.sh          # только новые/изменённые версии
/usr/local/bin/sync_mikrotik_repo.sh force    # игнорировать маркеры и перепроверить (чинит повреждённое)
/usr/local/bin/download_ros.sh 7.20.3         # одну конкретную версию в routeros/7.20.3/
/usr/local/bin/download_ros.sh 6.49.23        # старые релизы тоже поддерживаются
```

Аргумент версии можно передать и вторым параметром (`download_ros.sh force 7.20.3`). Целое повторно не качается: локальный размер сравнивается с `Content-Length` сервера, а `.zip` проверяется `unzip -t`, поэтому обрезанный или повреждённый файл восстанавливается, а не остаётся в зеркале навсегда.

Что происходит за прогон:

1. Скрипт сравнивает локальные маркеры (`LATEST.6` / `LATEST.6fix` и `NEWEST7.stable` / `NEWESTa7.*`) с данными upstream.
2. Для каждой изменившейся версии загружаются `CHANGELOG`, `packages.csv` (ROS 7), `all_packages-<arch>-<version>.zip` с распаковкой, а также образы `routeros*.npk` и — для не-x86 архитектур на ROS 7 версии 7.12.1 и новее — `wireless-*.npk`.
3. Закачка идёт в `<file>.part` и получает настоящее имя только после проверки размера (для архивов — и CRC), поэтому прерванный прогон не оставляет полуфайлов в зеркале. Ответ маркера сверяется с шаблоном `<версия> <timestamp>` и иначе отвергается, оставшийся `*.new` удаляется в начале каждой проверки, а локальный маркер перезаписывается после полностью успешной загрузки релиза. Повышение релиза очищает и кэши версий прокси — устройства переспрашивают upstream.
4. Все опубликованные сборки Winbox раскладываются по `routeros/winbox/<version>/`.
5. В конце скрипт вызывает локальный эндпоинт прогрева: `wget ${SITE_URL}/routeros/ros-warmup.php?token=${WARMUP_TOKEN}`. Эндпоинт собирает все уникальные версии прошивок из базы устройств (`current_firmware`, `upgrade_firmware`, `last_new_version`), запрашивает у upstream нужные маркеры для каждой версии (для ROS 6 ≥ 6.49.19 — `NEWESTa6.*` вместо `NEWEST6.*`; для ROS 7 ≥ 7.12.1 — `NEWESTa7.*` вместо `NEWEST7.*`) и записывает ответы в файлы кэша. Записи моложе `cache_revalidate` пропускаются, старые перепроверяются и при изменении ответа выводятся как `CHANGE`; прогон завершает HTML-отчётом (OK/CHANGE/SKIP/FAIL на каждый запрос). Интернет-доступ самих устройств при этом не требуется.

Канал ROS 7 намеренно загружается дважды: `download_ros7 7.10` покрывает релизы до 7.12.1, а `download_ros7 7.12.1 a` — API `NEWESTa7.*`, введённое в 7.12.1. Они требуют разных `User-Agent` (`RouterOS <version>`).

Прогрев можно запустить вручную, например после смены `SITE_URL` или очистки кэша (оба токена должны совпадать):

```
curl "http://localhost/routeros/ros-warmup.php?token=YOUR_SECRET_TOKEN"
```

## 🛰 Прокси запросов версий

| Запрос                                                         | Обработчик         |
| -------------------------------------------------------------- | ------------------ |
| `/routeros/NEWEST6.{stable,long-term,upgrade}`, `NEWESTa6.*`   | `ros6-upgrade.php` |
| `/routeros/NEWEST7.{stable,long-term,upgrade}`, `NEWESTa7.*`   | `ros7-upgrade.php` |

Порядок обработки каждого запроса:

1. **Кэш** — проверяется ключ `<эндпоинт>_<запрошенная версия>` в `routeros/ros6.version.cache` / `ros7.version.cache` вместе с timestamp. Запись моложе `cache_revalidate` отдаёт `X-Cache: HIT`; старше — снова запрашивается у upstream, но остаётся запасным ответом, если upstream недоступен.
2. **Upstream** — запрос с `User-Agent: RouterOS <version>` и исходной query-строкой. Ответ проверяется регуляркой `^\d+(\.\d+)+\s+\d+` перед кэшированием. Успех — `X-Cache: MISS`.
3. **Запасной вариант** — если upstream недоступен или ответ некорректен, сначала отдаётся устаревшая запись кэша, при её отсутствии локальный маркер (`LATEST.6`, `LATEST.6fix`, `NEWEST7.stable`, `NEWESTa7.long-term`), а если и его нет — значение из `mt_proxy_config.php`. Ответ уходит с `X-Cache: STALE`, событие попадает в `error_log`, некорректными данными кэш не перезаписывается.

Параметр `?version=` важен: MikroTik возвращает новее релиз *относительно версии, которая сейчас стоит на устройстве*, поэтому в кэше хранится отдельная запись для каждой пары «канал + версия».

Переход с ROS 6 на ROS 7 объявляется через `NEWEST6.upgrade` / `NEWESTa6.upgrade`. Если такая проверка не пройдёт, а запасное значение будет неверным, устройства либо не увидят ROS 7, либо получат его слишком рано.

## 🚦 Политика обновлений

Фильтр политики — `force_update.php`. Скрипт `BackupAndUpdate`, установленный на устройстве, отправляет запрос вида:

```
/routeros/force_update.php?new_version=7.24.5&model=RB4011iGS%2B&serial=XXXXYYYY&name=HQ%20router&currentFirmware=7.20.3&upgradeFirmware=7.24.5
```

Каждый запрос с непустым `serial` обновляет запись устройства, его IP-адрес (берётся из соединения), версии прошивок, имя устройства и последнюю предложенную версию. Так инвентарь наполняется автоматически, без какого-либо сканирования. Модель и имя устройства скрипт экранирует percent-encoding, поэтому имена с `&`, `+`, пробелами и т. п. передаются корректно. Ответ — простой текст: `ENABLED` или `DISABLED`.

Приоритет правил:

| # | Правило                       | Поведение                                                        |
| - | ----------------------------- | ---------------------------------------------------------------- |
| 1 | Список устройства по `serial` | Непустой список финален: разрешены только перечисленные версии   |
| 2 | Правило модели `model:<MODEL>`| Непустой список финален                                          |
| 3 | Таблица `global_versions`     | Разрешает перечисленные версии всем, кто не сопоставлен выше     |
| 4 | Legacy `mt_proxy_rules.php`   | Глобальный список из старого файла правил, если он ещё на месте  |
| 5 | `allowed_versions_hardcoded`  | Встроенные значения: `6.49.23`, `7.24.5`, `7.23.8`               |

Пустой список на любом уровне проваливает проверку на следующий, поэтому для новых зарегистрированных устройств решающим становится глобальный список. Если при вычислении политики возникло исключение, ответ — `DISABLED`: безопасное поведение по умолчанию — не трогать рабочий роутер.

## 🖥 Веб-админка

Откройте `http://<зеркало>/mt-proxy/` и авторизуйтесь (Basic Auth). Интерфейс не использует сессии и доступен только через защищённый каталог.

**Устройства** — добавленные автоматически (`auto`), вручную (`manual`) или импортированные из старого файла правил (`legacy`): модель, текущая и целевая прошивки, IP-адреса с историей во всплывающей подсказке, комментарий, разрешённые версии и время появления. Поддерживается поиск (в том числе по IP), редактирование и удаление отдельных строк — IP-адреса тоже можно редактировать в форме устройства, — а также пакетная *замена* или *дописывание* списков версий через чекбоксы.

**Global versions** — флотский allow-лист версий. Ввод по одной версии на строку; запятые тоже принимаются. Удаление применяется сразу.

**Current versions** — на странице показаны версии прошивок, которые прокси предлагает прямо сейчас (читаются локальные маркеры). Клик по версии открывает её `CHANGELOG` (отдаёт `changelog.php` из зеркалируемого каталога `<version>/CHANGELOG`), чтобы вы могли ознакомиться с релизом до добавления в allow-лист.

## 🔧 Настройка устройств

Статические DNS-записи на каждом роутере (или на внешнем DNS-сервере) перенаправляют оба имени на зеркало:

```
/ip dns static add address=192.168.0.1 name=download.mikrotik.com
/ip dns static add address=192.168.0.1 name=upgrade.mikrotik.com
/ip dns cache flush
```

Готовый вариант — `addons/mikrotik/dns.rsc`; перед импортом замените `SERVER_IP`.

После этого ручные обновления работают как обычно. На ROS 7 клиент обновлений по умолчанию использует HTTPS, поэтому выставьте `/system package update set mode=http`, чтобы устройство принимало HTTP-ответы зеркала (`BackupAndUpdate` делает это автоматически):

```
/system package update check-for-updates
/system package update install
```

### Скрипты резервного копирования и обновления

| Скрипт                     | Назначение                                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------|
| `BackupAndUpdate`          | Ежедневный цикл: проверка зеркала, создание резервных копий, установка обновлений RouterOS и прошивки RouterBOARD. Работает на ROS 6 и ROS 7 по HTTP или HTTPS |
| `BKPUPD-UPDATER`           | Скачивает с зеркала актуальный `BackupAndUpdate` и файл `BackupAndUpdate.md5`; переустанавливает скрипт только если контрольная сумма изменилась. Запускайте вручную или по своему планировщику. Автоматическое расписание намеренно не создаётся — из соображений безопасности |
| `install_updater.rsc`      | Установщик: скачивает по HTTPS (без проверки сертификата на этом шаге), импортирует и запускает `BKPUPD-UPDATER`                                        |
| `install_updater-http.rsc` | Тот же установщик по обычному HTTP — для первоначальной установки до настройки TLS                                                                     |

Перед публикацией скриптов замените `SERVER_NAME` на имя хоста вашего зеркала. Оба скрипта для устройств по умолчанию используют `http://SERVER_NAME`. Чтобы перевести проверку политики и обновление скриптов на TLS, измените URL сервера в скриптах на `https://…`: тогда helper загрузки проверяет сертификат, а устройства ROS 6 при первом запуске автоматически скачивают `fullchain.pem` и импортируют его в хранилище сертификатов. ROS 7 использует системное доверительное хранилище — CA должен в него входить или импортируется вручную.

Для работы updater'а на зеркале нужны оба файла: `BackupAndUpdate.rsc` **и** `BackupAndUpdate.md5`. Контрольная сумма не генерируется автоматически; пересоздавайте её после каждого изменения скрипта:

```
cd /var/www/html/routeros
md5sum BackupAndUpdate.rsc | awk '{print $1}' > BackupAndUpdate.md5
chown www-data:www-data BackupAndUpdate.md5
```

Самый быстрый способ развёртывания — один раз импортировать на устройство `BKPUPD-UPDATER` (через `install_updater.rsc` или `install_updater-http.rsc`): остальное будет скачано и обновится автоматически.

```
/ip dns static add address=192.168.0.1 name=download.mikrotik.com
/ip dns static add address=192.168.0.1 name=upgrade.mikrotik.com
/system script run install_updater      # после импорта addons/mikrotik/install_updater.rsc
```

Как работает `BackupAndUpdate`:

1. Регистрирует планировщик `BKPUPD-DAILY` на `05:00` и читает из его поля `comment` сохраняемые между запусками счётчики ошибок (`fw,os,osver`). Каждое устройство сначала выжидает детерминированную задержку 0–599 с, вычисленную из серийного номера, — чтобы парк не обновлялся одновременно.
2. На ROS 7 перед `check-for-updates` выставляет `/system package update set mode=http`, чтобы устройство принимало ответы прокси по обычному HTTP.
3. Отправляет на `force_update.php` модель, серийный номер, имя устройства, текущую и целевую прошивки и предложенную версию (по умолчанию HTTP; при настройке — HTTPS с проверкой сертификата, см. выше). Если ответ — `DISABLED` или сервер недоступен, обновление RouterOS отменяется. Состояние устройства сообщается при каждом запуске, даже если обновления нет.
4. Если обновление разрешено, сначала создаётся планировщик-защита от цикла перезагрузок, затем выполняются `system backup save` и `/export` с именем `auto-backup-<serial>-<version>-<date>` (в `flash/`, если доступно) и удаляются старые файлы `auto-backup-*`.
5. Отдельно, при `current-firmware != upgrade-firmware`, обновляется прошивка RouterBOARD.
6. Команды, ведущие к перезагрузке (`/system package update install`, `/system reboot`), — самые последние в скрипте.

**Защита от цикла перезагрузок:** каждая попытка увеличивает счётчик в поле `comment` планировщика. После `maxTries` (2) подряд неудачных попыток скрипт перестаёт перезагружать устройство. Разобравшись с причиной, сбросьте счётчики:

```
/system scheduler set BKPUPD-DAILY comment=""
```

## 📝 Логирование

Всё пишется в syslog (`daemon`) с тегом по имени скрипта. Отдельных лог-файлов, требующих ротации, нет. PHP-эндпоинты и отчёты прогрева попадают в error.log веб-сервера.

```
journalctl -t sync_mikrotik_repo.sh -f   # синхронизация
tail -f /var/log/nginx/mirror-error.log  # промахи прокси, запасные ответы, ошибки PHP
```

Полностью отключить логирование скриптов — `LOG_OFF=1` в `config.sh`.

Заголовок `X-Cache` — самый быстрый способ понять, какой слой ответил устройству:

```
curl -sI "http://localhost/routeros/NEWESTa7.stable?version=7.24.4" | grep -i x-cache
```

## 🐛 Устранение неполадок

| Симптом                                    | Что проверять                                                                                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Ничего не скачивается                      | Доступен ли `upgrade.mikrotik.com` с сервера? Установлен ли `wget` (выход `100`)? Можно ли создать `TARGET_DIR` (выход `101`) и писать в него (`102`)? Не занят ли лок другим прогоном (`Another synchronisation is already running`)? |
| Версия скачивается на каждом прогоне       | Скорее всего upstream перевыпускает релиз под тем же именем (меняется timestamp маркера), либо локальные файлы не проходят проверку размера/CRC и восстанавливаются. `CHANGELOG` и `packages.csv` качаются заново всегда.            |
| Нет `wireless-*.npk`                       | Эти пакеты загружаются только для ROS 7 версии 7.12.1 и новее на не-x86 архитектурах.                                                                            |
| Устройство сообщает «обновлений нет»       | Сброшен ли DNS-кэш? `/routeros` раздаётся из **корня сайта**? Есть ли заголовок `X-Cache`? Если нет — сломана маршрутизация PHP.                                 |
| Устройство получает неверную версию        | Посмотрите строку `<эндпоинт>_<версия>` в `routeros/ros6.version.cache` / `ros7.version.cache`: она перепроверяется по достижении `cache_revalidate` и автоматически стирается, когда синк повышает релиз. Чтобы ускорить — удалите строку вручную.  |
| Прогрев ничего не делает                   | `ros-warmup.php` вернёт 403, если токен в запросе не совпадает с `WARMUP_TOKEN` в `mt_proxy_config.php`; синхронизируйте его со `scripts/config.sh`. При пустой базе устройств прогревать тоже нечего. |
| `403` при скачивании `.rsc`-скрипта        | Ожиданно для браузера и `curl`: `/routeros/*.rsc` отдаётся только User-Agent'ам RouterOS (`Mikrotik/x.y…Fetch`, `RouterOS 7.x…`).                                 |
| Winbox не загружается                      | Установлен ли `curl`? Доступен ли `https://mikrotik.com/download/winbox`?                                                                                          |
| Веб-админка отдаёт 404                     | `FallbackResource` / `try_files` должны указывать на `index.php`. SQLite должна быть доступна записи пользователю веб-сервера; режим WAL требует записи в каталог. |

## 🔒 Замечания по безопасности

- Статический DNS делает так, что все устройства в сети доверяют этому хосту. Не выставляйте зеркало в недоверенные сегменты без контроля доступа.
- Эндпоинт прогрева кэша защищён только общим секретом. Замените `CHANGE_ME` в `WARMUP_TOKEN` **в обоих** файлах — `scripts/config.sh` и `html/mt-proxy/mt_proxy_config.php`, — иначе любой, кому доступен URL, сможет инициировать запросы к upstream с произвольными параметрами версии.
- `BackupAndUpdate` / `BKPUPD-UPDATER` импортируются с полным набором политик RouterOS (`ftp,reboot,read,write,policy,test,password,sniff,sensitive,romon`) и могут перезагружать устройства. Кто может изменить `/routeros/BackupAndUpdate.rsc`, тот потенциально контролирует весь парк, крутящий updater. Ограничивайте доступ к самому серверу; конфигурация веб-сервера отдаёт `.rsc`/`.txt` только User-Agent'ам RouterOS, но атакующий уже на хосте-зеркале остаётся риском.
- Веб-админка защищена только Basic Auth и правилами vhost. Держите её вне публичного Интернета, ограничьте по IP источника и используйте надёжный пароль.
- `mt_proxy_config.php` теперь содержит секрет (`WARMUP_TOKEN`), а `mt_proxy.db` — инвентарь устройств (серийные номера и IP). Обе конфигурации vhost блокируют прямой доступ к базе; храните резервные копии вне корня документов и защищайте PHP-конфиги от раскрытия исходного кода.
- По обычному HTTP проверка политики передаёт метаданные устройства (серийник, модель, прошивки) в открытом виде. Используйте HTTPS (и CA-цепочку), если путь от устройств до сервера не полностью доверенный.

## ⚠️ Известные ограничения

- **Перепроверка кэша не мгновенна.** `ros6.version.cache` / `ros7.version.cache` хранят `значение|timestamp`: запись отдаётся как `X-Cache: HIT`, пока её возраст меньше `cache_revalidate` (по умолчанию 6 часов), затем снова запрашивается у upstream. Релиз, повышенный скриптом синхронизации, кэши очищает сразу, но версия, вышедшая между двумя прогонами, доходит до устройств при первом запросе после истечения TTL.
- **Целостность проверяется только по размеру, CRC и формату маркера.** Закачка инкрементальна: целый локальный файл (совпадает `Content-Length`, архив не повреждён) повторно не качается, поэтому пакет, заменённый MikroTik на *другую сборку того же размера*, будет замечен только по новому timestamp маркера. Чтобы принудительно перекачать всё, удалите `${TARGET_DIR}/<version>/`; контрольных сумм от вендора нет.
- **Автоматически зеркалируется только новейший релиз канала.** Старые версии остаются на диске, но цикл синхронизации отслеживает только `LATEST.*` / `NEWEST*; перекачайте конкретную версию через `download_ros.sh`.
- **Список архитектур статичен.** Новые типы машин нужно добавлять в `firmware_arch` вручную, иначе их пакеты молча пропускаются.
- Скрипты работают от root, cron делает `chown www-data`. Развёртывание предполагает, что зеркалом управляет root; режима установки без привилегий нет.
